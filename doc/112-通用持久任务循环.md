# 阶段 112：通用持久任务循环

## 1. 当前结论与里程碑状态

阶段 112 的 112A、112B、112C 三个内部里程碑均已完成。112A 建立版本化多步骤规划证明；112B 把阶段 111 保存的 `MULTI_STEP_PLAN_DEFERRED` 从不可执行 preview 续接到服务器裁决的 `Execute → Verify → Delivery` 持久闭环；112C 再接入精确 Patch/Test/Approval、有界 Repair、持久 no-progress 与预算终止。整个过程仍不会第二次调用 Turn Planner Provider，也不会把模型提案、组合 Contract、失败结果或 UI 状态视为执行授权。

最终通用循环要求 expected generation-1 Plan、逐 source-step 权限交集、当前 runtime eligibility、ExecutionRun、节点 attempt、审批/副作用回执和 verified ResultRef 在同一证明链中闭合。普通非审批节点失败只可在原 Plan retry 与预算内进入有界 Repair；任何写入都仍要取得绑定当前 revision 和 preview 的 fresh confirmation。

```text
阶段 111 持久用户消息
        │
        ├─ 单个 Offer ──> 继续走阶段 111 的 trusted recipe 单步绑定
        │
        └─ 2～8 个 Offer ──> MULTI_STEP_PLAN_DEFERRED（不可执行来源锚点）
                                │
                                ▼
                    重验消息片段、Offer、recipe、Policy 与预算
                                │
                     （零第二次 Provider 调用）
                                │
                                ▼
                   TaskLoop Observe → Plan / Failed
                                │
                                ▼
                  model_planner Draft + generation-1 preview
                                │ 112A
                                ▼
                  source-step authority / runtime eligibility
                                │
                                ▼
                 generation-1 Plan + Run 原子激活
                                │
                                ▼
             Execute → Verify → verified ResultRef → Delivery
                                │ 112B
                                ▼
                  waiting_user / Patch receipt reconcile
                                │
                     bounded Repair / stable stop
                                │ 112C
                                └─ 回到 Execute 或终止
```

因此，“阶段 112 规划支持 1～8 步”的准确含义是：**单步骤继续由阶段 111 的稳定路径完成，多步骤 TaskLoop 入口处理 2～8 个 Offer**。不把单步强行迁入 TaskLoop，避免改写阶段 111 已验收的 digest、行为和 Plan Binding。

截至 2026-08-24，112A、112B 已分别以中文里程碑提交收口；112C 代码、文档和阶段 112 最终全量/外部门禁均已通过。阶段 checkpoint 使用中文提交，不自动 push；下一步从该提交创建 `codex/stage-113`。

## 2. 不可变来源与零模型重放

`MultiStepPlanRuntime` 只接受阶段 111 已经终结为 `multi_step_deferred` 的精确证明。`TurnPlannerRuntime.revalidate_deferred_plan` 会重新读取并核验：

- Task、持久用户消息 ID/摘要及所有参数原文片段；
- terminal Planner Run、Adjudication 和 Turn Plan Binding 的 ID、摘要与相互血缘；
- ordered Offer key、Offer manifest、trusted Route recipe 与 route version；
- exact Contract、执行 Agent/Prompt、Capability、Provider snapshot、Policy snapshot、预算及 expected Plan binding；
- 参数绑定的 canonical proof，且每个值仍逐字来自原持久用户消息。

重验不会创建新的 Planner Run，也不会调用 Model Gateway 或 Provider。阶段 111 的 Run/Adjudication/Binding 保持原样，112A 只在其后追加来源引用、TaskLoop 事件与组合 Draft。重复推进、进程重启恢复和并发 worker 收敛到同一内容寻址结果；终态失败保存 `never_automatic` 失败证明，不通过隐藏重试重放 Planner。

## 3. 服务器 Model Planner Composer

`ModelPlannerComposer` 的输入是 2～8 个已经重新验证的 `RevalidatedOfferStep`，模型不能再次提交图、Capability、命令、路径或权限。Composer 负责：

- 按原 adjudication 顺序为节点与 acceptance criterion 增加 step namespace；
- 重新编译每个 source recipe，并逐项比对 Offer、source expected Plan、Policy 和参数绑定；
- 将各步骤组合为确定性、有序 DAG，最终只保留一组服务器生成的 final acceptance 与 delivery；
- 合并 Task Contract 时，为描述完整任务而受限聚合 Capability/resource scope、最高 classification、egress/export 与 allowed domain 等任务声明；仅允许的 privacy modes 与 Provider locations 取交集且交集为空时拒绝。组合 Contract 本身不产生可执行授权，112B 的节点有效权限必须再取 `组合 Contract ∩ source-step 权限`；
- 对节点数和所有预算做守恒求和，超过领域上限直接失败，不截断步骤、不钳制预算；
- 生成 producer 为 `model_planner / deskpilot.offer-composer.v1` 的 DraftPlan；
- 用现有纯确定性 PlanCompiler 生成并复核 expected generation-1 ExecutablePlan preview。

每一步都保存 Offer、recipe、source Plan、Policy、预算、参数摘要和 source→composite node mapping 的精确绑定。参数正文只存在内部证明中；公开 Workbench 投影不返回这些内容。

## 4. `0052`～`0054` 持久化模型

Alembic `0052_model_planner_task_loop` 以 `0051_turn_planning_offers` 为父版本，新增四张表：

- `task_loops`：当前 `observe/plan` 指针、revision、最新事件摘要、active Draft 或失败证明；
- `task_loop_events`：不可变的 `observed → plan_bound/plan_failed` 两事件摘要链；
- `model_planner_drafts`：组合 Task Contract、`model_planner` DraftPlan 与 expected generation-1 preview；
- `model_planner_step_bindings`：逐步骤 Offer/recipe/Policy/budget/parameter/node-map 内部证明。

数据库约束将 TaskLoop 锚定到同一 Task、用户消息、Planner Run、Adjudication 与 Turn Plan Binding；同一 source binding 只能产生一个 Loop/Draft，step ordinal 有界且同一 Draft 内不重复 Offer。应用读取还会重建领域模型，进一步要求 ordinal 连续，并逐一核验 duplicated columns、manifest、摘要链、Draft、步骤映射与 expected Plan；任何漂移都 fail closed。存在 `0052` 数据时 downgrade guard 拒绝丢失式降级。

`TaskLoop` 当前只有三个状态：

- `observed`：revision 1，可由协调器恢复并继续服务器组合；
- `planned`：revision 2，Draft/preview 已封存，但不可执行；
- `failed`：revision 2，稳定失败且禁止自动重放。

Alembic `0053_task_loop_execution` 继续以 `0052_model_planner_task_loop` 为父版本，新增 112B 的执行真值：

- `model_planner_node_bindings`：逐 composite node 封存 exact source Offer/recipe/Policy/input、source→composite mapping、`组合 Contract ∩ source-step 权限` 和当前 runtime eligibility；
- `task_loop_executions` 与 `task_loop_execution_events`：绑定 generation-1 Plan/Run、revision 和不可变 `activated → ... → succeeded/failed` 摘要链；
- `task_loop_node_attempts`：保存 prepared/claimed/running/awaiting_verification/verified/failed、owner/fence、超时和稳定失败；
- `task_loop_verified_results`：保存类型、payload digest、Plan/Run/Node/Attempt/Invocation/Capability 血缘闭合的 verified ResultRef；

Capability 执行的准备输入与完成回执被封存在对应 `task_loop_node_attempts`，外部 I/O 始终发生在短事务之外；完成事务再复核 owner/fence、binding、输入与 receipt 摘要并生成 ResultRef。

激活事务会再次重建 expected Plan，逐节点复核 source binding、有效权限、输入 manifest 和当前 Registry 快照，然后原子创建 PlanningState、PlanGeneration、ExecutionRun、ExecutionNode、所有 node binding、首个 execution event 与 TaskLoop execution 指针。任一证明不匹配时保持 112A Draft 不可执行；不会先创建 Run 再补权限。

Alembic `0054_task_loop_cycle_events` 以 `0053_task_loop_execution` 为父版本，新增 112C 的持久循环真值：

- `task_loop_capability_approvals`：逐节点保存 exact Task、execution/revision、Plan/Run、node/attempt、Capability、staging manifest、preview digest、fresh confirmation、批准/拒绝状态和审批摘要；同一节点只存在一条当前审批链，旧 revision 或旧 confirmation 不能复用；
- `task_loop_cycle_events`：保存 no-progress、预算终止以及 `repair_started/repair_completed` 的不可变事件与摘要，使恢复过程可以区分“尚未决定”“已开始 Repair”和“已完成 Repair”。

通用 Workspace Patch executor 在写入前只生成服务器约束的 staging/preview；审批通过后才执行精确副作用。若进程在文件写入后、结果落库前中断，恢复会按同一 attempt 和内容寻址 Patch receipt 对账，绝不把 outcome unknown 当作可安全重放。普通非审批节点的 transient failure 最多使用原 Plan 声明的 retry 预算，并受 TaskLoop 最多两次 Repair 限制；审批副作用、预算耗尽或 no-progress 不进入通用自动 Repair。

## 5. Workbench、恢复与隐私投影

Workbench 保留 `plan_task_loop` 和 `advance_task_loop`，增加绑定 exact Task/revision/confirmation 的 TaskLoop 审批 action 与可空 `task_loop` 执行投影。后台协调器会把 `observed` Loop、仍可建立 Loop 的 deferred Task，以及 planned/active/awaiting_user/repairing execution 纳入启动/周期恢复；恢复只重验持久证明和确定性 reducer，不重放 Turn Planner Provider，也不会透明重放 outcome unknown 的副作用。

激活前继续返回兼容的 `deskpilot.task-loop-workbench.v1` 计划投影；激活后切换为脱敏的 `deskpilot.task-loop-execution-workbench.v1`，只包含：

- phase、status、revision、event count、step count 与 recoverable；
- Plan/Run/execution/binding/progress 摘要，节点状态、attempt 数、verified ResultRef 数和等待审批摘要；
- 持久 repair count、最大计划代数、no-progress count 与预算状态；
- 稳定失败码、reason、`never_automatic` 和 failure digest；
- 更新时间。

投影明确不包含用户输入/参数值、Offer、recipe、Provider/claim 私有信息、Task Contract、DraftPlan/ExecutablePlan 正文、逐节点映射、ResultRef payload 或内部 Policy。前端按同一 Task ID 展示 `Observe / Plan / Execute / Verify / Delivery`、节点状态和截断摘要；旧计划态文案仍明确提示“尚未启动执行”。

## 6. 112A～112C 的安全边界

- 单步保持阶段 111 路径，112A 不改写历史 adjudication、binding 或 Phase75 v16 baseline。
- 模型选择 Offer 仍不授予权限；组合 Contract 和 expected Plan 都只是服务器裁决的计划证明。
- 112A 不创建 active Plan generation、ExecutionRun、Invocation、Tool call、Approval 或副作用回执。
- Composer 失败不会退回更宽 Capability，也不会只执行可组合步骤的前缀。
- Provider timeout/unknown 的处理仍属于阶段 111；112A 没有第二次 Provider 调用。
- 任意 Shell、安装、删除、登录态浏览器和自由 executable/argv 继续关闭。

112B 额外锁定：

- `CapabilityExecutorRegistry` 只接受服务器注册的 exact Capability/版本与不可变 executor manifest；模型不能提供 executable、argv、cwd、环境变量或新 Capability。
- `CapabilityInputBindingCatalog` 只从对应 source-step 的已验证参数和上游 verified ResultRef 构造输入；其他步骤的输入、Memory、Summary 或 UI 文本不能横向注入。
- `TaskLoopAgentAdapterRegistry` 按 exact Agent identity 绑定既有受控 Runtime。Agent 候选输出仍要由服务器 bridge 转成 verified ResultRef，不能直接完成节点。
- 研究、知识、固定 MCP、Workspace 读取/检查/固定测试和 Artifact/Browser 能力通过同一 reducer 推进；final acceptance 会逐项语义预检 ResultRef，delivery 只消费通过预检的输出。
- 每次 `advance_task_loop` 最多执行一个持久 reducer command。进程重启会从 execution/node/attempt 真值继续，不依赖内存中的 Route 分支；稳定失败会封存并终止，不隐藏重试。
- Windows worker 对长路径只在本地文件 I/O 时使用 extended path 表示，Capability root、ACL、AppContainer 和内容摘要边界不变；这不是路径权限放宽。

112C 额外锁定：

- Patch 参数仍逐字来自已持久化用户消息和服务器 Offer；模型不能借 Repair 生成新路径、命令、环境变量、Capability 或授权事实。
- `waiting_user` 只表示等待 exact fresh confirmation，不代表已批准。审批必须复核当前 Task、execution revision、node/attempt、preview、manifest 与确认摘要；过期或重复审批 fail closed。
- Patch receipt 是副作用对账依据，不是模型声明；只有与 exact attempt/manifest/内容摘要闭合的 receipt 才能恢复为 verified ResultRef。
- Repair 只消费已保存的失败 attempt，并先持久化 `repair_started`。恢复会完成同一 marker，不重复决定或重放 Planner；每个 execution 最多两次 Repair，且不能突破原 Plan retry/预算。
- 审批节点的失败、取消、unknown 副作用、预算耗尽和连续三次 no-progress 都稳定终止或等待人工处理，不进入透明自动 Repair。

## 7. 阶段 112 已闭合的硬安全门槛

112B 没有仅凭组合 Task Contract 调用 Executor。开始激活任何节点前，同时满足：

1. **逐 source-step 最小权限绑定**：每个 composite node 必须绑定其精确 source Offer、recipe、Policy、输入证明和 source→composite node mapping；有效权限按 `组合 Contract ∩ source-step 权限` 计算，不能把其他步骤的 Capability/egress/Workspace 权限横向借给当前节点。
2. **当前运行时资格复核**：激活前重新检查 exact Agent/Prompt/Capability、Executor 注册、Provider/runtime 可用性和当前 Policy；仅证明 Capability 曾存在于 Catalog 不足以执行。
3. **原子封存后才激活**：expected generation-1 Plan、逐节点 source binding、执行状态和首个可运行节点必须在同一受保护边界闭合；不能先创建 Run 再补权限证明。
4. **只消费 verified ResultRef**：下游节点只接收类型、digest、Plan/Run/Node/Invocation/Capability 血缘全部闭合的 ResultRef；模型文本、Memory、Summary、MCP/UI 内容不能代替 verified edge。
5. **恢复与副作用隔离**：外部 I/O 不在数据库事务内执行；attempt、owner/fence、超时、取消、no-progress 与预算终止都要有持久真值，重启不得透明重放 outcome unknown 的动作。

6. **审批与 Repair 不扩权**：审批只消费 exact 服务器 preview，Repair 只消费失败证明和原 Plan retry/预算；两者都不能授予新 Capability、路径、命令或 Provider 权限。

这六项已经落实为 activation/runtime/reducer/approval/cycle event 的持久证明门。未满足时，112A Draft 保持不可执行 preview，或已激活 execution 进入等待人工/稳定失败，不会降级为更宽的 Route/Capability。

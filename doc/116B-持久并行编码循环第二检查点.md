# 阶段 116B：持久并行编码循环第二检查点

## 1. 检查点结论

116B 第二个代码检查点已落地：固定 `workspace_coding_loop` 在并行 Reader 与写入 Capability 之间新增两个真实、持久、LOCAL-only 的 Patch Planner Model Turn/Handoff；同会话新用户指令会先封存旧 TaskLoop generation 与全部未完成租约，再把旧 Contract/Plan/Execution 的终止证据绑定到新的不可变 Task/用户消息；成功交付通过既有 Workbench/API 返回脱敏 diff、测试、风险和回滚点投影。

本检查点闭合了第一检查点明确列出的 Patch Planner、amendment fencing 和公开 Delivery 投影，但仍不把整个 116B 标记完成。当前协调顺序仍由服务器固定 DAG 与持久 Reducer 决定，没有把 Dynamic Coordinator 的模型图提案接入这条纵切；依赖安装、Git branch/commit、自由 Shell、真实 cloud 模型质量与生产激活也未开放。

## 2. Patch Planner 的真实 Model Turn/Handoff

固定 DAG 更新为：

```text
inspect_primary      inspect_secondary
       |                    |
plan_primary_patch  plan_secondary_patch
       \                    /
        +-- verified join --+
                apply_patch
                     |
              run_fixed_test
                     |
             final_acceptance
                     |
                  delivery
```

- 两个 `builtin.workspace_patch_planner@1.0.0` 节点分别绑定一个已验证 Reader ResultRef、一个服务器封存的精确 `old_text → new_text` Offer 和 `workspace.patch.propose.v1`；
- Patch Planner 通过现有 `AgentModelLoopRuntime` 创建真实持久 Invocation、Handoff、ModelTurn、dispatch attempt 和 Decision，不再由测试直接伪造候选；
- 模型只能返回与服务器 Offer 完全一致的单文件结构化提议，不能改变路径、增加文件、提供 executable/argv/env、获得 Patch approval 或直接写工作区；
- 独立 bridge 会重验 Agent/版本、source node、request/response/schema digest、Decision binding、AgentOutputResult 和精确 replacement，再签发 `PATCH_PROPOSAL` ResultRef；
- 写入节点必须消费两个唯一、已验证、路径与封存变更完全一致的 Patch Proposal ResultRef。模型提议不是执行授权，原有 preview/confirmation/approval、原子写入和 receipt 边界保持不变；
- 重启后从持久 ModelTurn/Decision/ResultRef 恢复，不重放已成功的 Planner 调用。

## 3. 同会话 amendment 与迟到结果 fencing

Workbench 收到正在恢复中的 coding TaskLoop 的新用户消息时，按以下顺序执行：

1. 取消后台 auto-advance；
2. 先取消底层 `TaskExecutionRun` 并提升 node fencing token，使旧 worker 的后续 mutation 立即失效；
3. 将仍在 `dispatching` 的 ModelTurn/dispatch attempt 标记为 `outcome_unknown`，不透明重放；其余未完成 Attempt 标记为 `cancelled`；
4. 为旧 TaskLoop 追加不可变 `cancelled` 事件并进入不可恢复终态；
5. 在同一 Conversation 创建新的不可变 Task 和用户消息，按新指令重新路由；
6. 写入 `WorkspaceCodingAmendmentBinding`，绑定源 Task、Contract version/digest、Plan generation/digest、Execution/event digest、后继 Task 和后继消息 digest。

这保持了阶段 77 已确定的语义：同会话修订不是原地改写旧 Contract，而是建立新的不可变后继 Task。`0059_workspace_coding_amendments` 通过复合外键约束 exact Contract、Plan 和终止事件；同一源 Execution 只能有一个后继，同一后继 Task/消息也只能被绑定一次。重复请求只接受完全相同的证明，消息或摘要漂移会 fail closed。表中存在记录时 downgrade 被拒绝。

## 4. 用户可见 Delivery 投影

成功 coding execution 现在通过既有 `TaskLoopExecutionRead`/Workbench 投影返回 `coding_delivery`，不新增第二套 API 或前端状态机。公开字段包括：

- 排序后的变更文件和精确 old/new diff；
- 每个文件的 Patch Planner Agent 版本、Decision digest 与 verification digest；
- 固定测试类型、attempt、项目/测试路径、状态和 exit code；
- 失败/Repair 历史及失败回执 digest；
- `local_fake_model_quality_unproven`、`git_commit_not_created` 等剩余风险；
- 每个文件是否存在回滚点及 previous/current version digest。

投影不返回 backup/staging 的内部相对路径、Capability authority manifest、执行凭据或模型上下文。读取时会从 `workspace_coding_deliveries` 重建并复验 exact execution、Plan、计数、manifest/delivery digest；成功的 coding TaskLoop 缺少交付证据也会拒绝读取，避免“执行成功但没有证据”的假完成。

## 5. 兼容与安全边界

- 非 coding TaskLoop、旧历史读取和既有 Command Plan 继续使用原模型；`coding_delivery` 为可选字段，只有成功 coding execution 才允许出现。
- 已验证失败回执投影从“仅 Command 节点”推广为所有 Capability 节点，以支持固定测试失败后的 Repair 历史；它没有改变依赖解锁规则，只有 passed ResultRef 可满足后继边。
- 本检查点只使用 LOCAL-only Agent、Fake Provider、服务器固定路径和隔离测试仓库；没有 live capture、Production Admission、cloud activation、baseline 改写或 push。
- Dynamic Coordinator 尚未作为模型节点接入本固定 DAG。当前服务器编译 DAG/Reducer 是唯一调度真值，不能把它描述成已经完成的模型协调器。

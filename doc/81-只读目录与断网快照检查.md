# 阶段 81：只读目录与断网快照检查

阶段 80 已能在对话中读取文件、预览并确认多文件精确补丁，但修改后仍缺少验证入口。阶段 81 增加只读目录列表和固定快照检查，把“定位文件 → 读取 → 补丁 → 验证”接入同一个 Conversation Turn Router。

本阶段没有开放自由 Shell，也没有把任意 `pytest`、`vitest` 或仓库脚本伪装成安全能力。首版检查只解析一份受限文本快照，不向隔离进程暴露工作区路径，更不执行仓库代码。

## 1. 对话 Route

首版固定语法为：

```text
列出工作区目录：backend/src
运行工作区检查：python-syntax backend/src
运行工作区检查：json-parse frontend/package.json
```

`workspace_directory_list@1` 和 `workspace_snapshot_check@1` 都是 R0 Capability。分类器只接受上面的确定性参数形状；检查 profile 只有 `python-syntax` 与 `json-parse`。模糊命令、额外参数、未知 profile 或不匹配的文件类型都 fail closed。

两个 Route 继续绑定原始消息摘要、classifier version、Route manifest、Capability、Contract、Plan、Run 和 result digest。每个新 Turn 仍产生新的不可变 replacement Task，不会改写旧 Task 的事实。

## 2. 只读目录边界

目录读取只返回指定目录的直接子项，不递归展开，也不返回文件内容：

- 仅允许显式 Conversation Workspace 根目录下的规范相对路径；`.` 表示该根目录；
- 拒绝绝对路径、`..`、点前缀路径段、符号链接和 Windows reparse point；
- 隐藏项、链接、非白名单文件类型和超过单文件上限的文件不进入结果；
- 最多扫描 1000 个目录项、返回 200 项，超过时显式标记 `truncated`；
- 目录读取前后复核稳定 stat identity，发生竞争时返回冲突而不是陈旧列表；
- 每项包含类型、相对路径、可选字节数和 version digest，整个列表再生成 result digest。

这个能力用于发现候选文件，不会把“看见一个路径”升级成写权限。

## 3. 有界快照

检查目标可以是一个匹配 profile 的文件，或一个目录。控制面先在工作区边界内建立稳定 UTF-8 文本快照：

- `python-syntax` 只选择 `.py`；`json-parse` 只选择 `.json`；
- 最多递归 8 层、扫描 1000 个目录项、包含 64 个文件；
- 单文件继续受 256 KiB 上限约束，整份快照最多 512 KiB；
- 隐藏项和 `__pycache__` 不进入快照，任一可见链接/reparse point 直接拒绝；
- 每个文件都通过句柄读取并复核读前/读后 identity，目录也复核遍历前后 identity；
- snapshot digest 绑定 profile、目标路径、文件路径、内容摘要和版本摘要。

隔离进程只收到这份内容寻址文本快照，没有工作区路径句柄，也不会在执行期间重新读取仓库。

## 4. 固定检查与强隔离

`python-syntax` 调用标准库 `ast.parse`，`json-parse` 调用标准库 `json.loads`。两者都只做解析，不导入模块、不调用插件、不执行测试发现、不运行 package script。

每次检查强制创建新的 Windows AppContainer worker，并要求网络隔离；不能取得该边界时能力不可用，不降级到普通子进程。运行约束为：

- AppContainer 网络访问关闭；
- Job Object 内存上限 128 MiB；
- 活动进程上限 1；
- 运行超时 10 秒；
- Worker 协议帧上限 1 MiB；
- 结构化结果上限 64 KiB、问题最多 64 项。

结果明确记录 profile、快照摘要、检查文件数、`passed`/`failed`、结构化问题、隔离模式、网络状态和 result digest。语法问题表示“检查操作成功完成但发现失败”，不会伪报为系统执行故障；隔离、协议或进程故障则按 Route 失败处理。

## 5. 前端证据

统一研究工作台没有改回表单式控制台。用户仍从底部对话框下达任务，消息流展示当前 Run；右侧证据区增加：

- 目录条目、类型、字节数与截断状态；
- 检查 profile、通过/失败、文件数和 snapshot digest；
- AppContainer 与断网事实；
- 结构化文件/行/列问题。

这些证据不使用聊天气泡伪装成普通回答。补丁审批仍必须由用户显式确认，检查也不会自动赋予下一次写权限。

## 6. 验收覆盖

自动化覆盖包括：

1. 两条 Route 的固定语法、参数绑定与模糊请求拒绝；
2. Capability/Contract/Plan 编译及运行时可用性门禁；
3. 目录排序、摘要、截断、隐藏项和链接边界；
4. 单文件与目录快照、类型匹配、深度/扫描/文件数/总字节限制；
5. Python/JSON 成功和结构化失败问题；
6. Turn API 的持久化、重载和证据投影；
7. 前端目录证据与隔离检查失败证据；
8. 真实 Windows AppContainer 断网烟测。

本阶段复用 `0037_turn_routes` 保存新的 Route result manifest，不需要数据库迁移。

最终验证结果：阶段 81 涉及的 30 项定向后端用例通过；Ruff 全仓通过，mypy 通过 217 个生产源码，Alembic 保持单一 `0037_turn_routes` head 且 autogenerate check 无新操作，`uv lock --check` 通过。真实 `json-parse` 烟测在 AppContainer 中返回 `passed / windows_appcontainer / network_access=false`。

后端全量收集 506 项，在 3 小时 36 分高负载运行中结果为 `493 passed, 12 skipped, 1 failed`。唯一失败是既有 `test_reconciliation_receipts_survive_restart_and_never_blindly_replay` 超过其 3 秒等待窗口、停在 `running`；该用例与本阶段 Route/快照检查无调用链关系，随后单独复跑通过。这里不把全量结果改写成退出码 0；后续应单独治理该已知慢测窗口。

前端 22 个测试文件/149 项、Vue type-check 和 production build 通过；工作台静态 `finesse-ui` 检测为 `p0: 0`，`git diff --check` 通过。按界面技能的组件范围约束，本次没有自行打开用户页面做视觉断言。

## 7. 诚实边界与下一阶段

阶段 81 形成的是最小“静态验证闭环”，不是完整代码测试闭环：多轮对话可以完成读取、补丁和检查，但系统不会在一次补丁提交后暗中自动跑检查；`python-syntax` 也不能证明业务逻辑正确。

真正的 `pytest`/`vitest` 会执行仓库代码、测试插件和依赖，风险远高于解析文本。后续若增加，应作为独立的签名测试 profile：在无凭据、默认断网、只读克隆工作区中使用精确 executable/argv 白名单、完整进程树限制、时间/输出/磁盘配额和脱敏回执。即使那时也不应开放自然语言自由 Shell。

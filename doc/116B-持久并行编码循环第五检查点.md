# 阶段 116B：持久并行编码循环第五检查点

## 1. 检查点结论

116B 第五个代码检查点已把第四检查点“精确两文件”的持久编码图推广为服务器预编译的 2～8 文件有界图。Python 和 Node 生态各有 2～8 文件的固定 Offer 变体；文件数、exact path、Reader/Planner 节点、依赖、预算与 Git 范围均由服务器派生，模型仍不能创造路径、命令或图结构。

这一检查点闭合了“2～8 个文件分批读取 → 分批 Patch 提案 → exact join → 一次 Patch 确认 → 固定测试/有界 Repair → 一次 Git 确认 → 本地 commit → Delivery”的固定多文件链。原两文件 Offer、Coordinator 合同、图摘要与 Delivery v2 继续保持，不用新实现改写历史证明。

## 2. 服务器封存的有界图

对任意 `N in [2, 8]`，服务器构造以下图：

```text
                         coordinate_coding
                                  |
              +-------------------+-------------------+
              |                   |                   |
        inspect_file_01     inspect_file_02     ... inspect_file_N
              |                   |                   |
      plan_file_01_patch   plan_file_02_patch   ... plan_file_N_patch
              \                   |                   /
               +---------- exact verified join ------+
                                  |
                         apply_patch (confirm #1)
                                  |
                           run_fixed_test
                                  |
                          commit_git (confirm #2)
                                  |
                          final_acceptance
                                  |
                               delivery
```

- Offer 不在模型返回后临时修改图，而是预编译 `workspace_coding_loop:<ecosystem>:<N>` 与对应 node variant。因此 Contract/Plan/Offer 摘要在规划前就可确定。
- `primary_path` 和 `secondary_path` 保持旧参数名；3～8 文件变体按需增加 `file_03_path`～`file_08_path`。参数集必须精确匹配变体，所有路径必须来自持久用户消息、位于同一项目且互不重复。
- Draft 业务节点数为 `2N + 6`，Coordinator 可见节点数为 `2N + 3`，可运行 binding 数为 `2N + 4`。上限 N=8 时仍低于新的 24 计划节点和 20 映射/binding 硬上限。
- TaskLoop 全局 batch 上限仍为 2：Reader 与 Planner 可分批并行，Patch、Test/Repair、Git 和 Final 仍严格串行。
- 一个 Reader/Planner 结果缺失、重复或摘要不匹配都不会被 join 采用；Patch 只能消费与 exact route changes 一一对应的 N 个提案。

## 3. Coordinator 与摘要兼容

- N=2 继续使用 `builtin.workspace_coordinator@1.1.0` 和原 decision schema，原 Contract 文案、预算、七节点图、Delivery v2 及其摘要不变。
- N>2 使用独立 LOCAL-only `builtin.workspace_bounded_coordinator@1.0.0` 和 decision schema v2。Coordinator 只能回显服务器封存的奇数 9～19 节点图，并以 `commit_git` 为唯一输出。
- 运行时从 Plan 和 exact path proof 重建整张图，对模型结果做全等校验；不接受“Schema 合法但少一个节点”或依赖/预算/输出节点漂移。
- Fake Provider 显式支持新 schema，所以本地端到端验收走的是真实 Model Turn/Handoff/ResultRef 通道，不是测试绕过 Agent Runtime。

## 4. 执行、Delivery 与 Workbench

- Patch input binding 现在携带 exact file count 和每文件 path proof。执行前重验项目、Plan/node、Reader/Planner ResultRef、route changes 与 staging，不唯信模型返回的变更集。
- 第四检查点的 Git Preview 本已允许 2～8 个文件；本检查点将其与 N 个已验证 Patch 提案和 N 个 rollback backup 做精确集合绑定。仍只能在服务器命名的本地新分支上提交，不 push。
- N>2 的交付升为 `deskpilot.workspace-coding-delivery.v3`，公开投影包含 `file_count`、N 个 Reader/Planner/变更证明、测试与 Git receipt。v1/v2 仍按原节点数、Coordinator 与无/有 Git 规则严格只读。
- Workbench 的 Delivery 数组上限从 2 扩展到 8，未新增独立 API 或前端页面。

## 5. 迁移与失败策略

- Alembic `0060_workspace_coding_bounded_files` 将 `workspace_coding_deliveries.changed_file_count` 的数据库约束从精确 2 扩展为 `BETWEEN 2 AND 8`；不新增第二套节点状态机。
- 存在 `changed_file_count <> 2` 的新记录时 downgrade 拒绝，防止恢复旧约束时丢失多文件交付证明。
- 任一路径、Catalog/Profile、Plan/node、Coordinator 图、Reader/Planner input proof、Patch 变更集或 Git receipt 漂移都 fail closed。
- 既有“失败回执不解锁后继、一次已知失败 Repair、running/outcome unknown 不透明重放”规则保持不变。

## 6. 诚实边界

- 已开放的是 14 个服务器预编译的 Python/Node 变体，不是模型自由选择任意文件数、路径或运行中改图。
- 端到端验收覆盖 Python 三文件跨目录任务，并在上限测试中编译八文件图；Node 变体已进入 Offer/Compiler/Runtime 同一实现，但尚未完成独立的 Node 多文件端到端任务。
- 当前仍没有广域项目探索后由模型提议文件集的安全收窄边界；用户/路由层需在规划前给出 exact 2～8 个文件。
- 自由 Shell、模型提供 argv/executable/env、依赖安装、删除、自动 push/PR 和 cloud activation 仍在范围外。
- 验收只证明 LOCAL-only/Fake 运行时语义。它不是 115B 真实 cohort 证据，也不是 116C 真实模型质量结论。

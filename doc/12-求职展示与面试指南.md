# 12. 求职展示、演示与面试指南

## 1. 项目叙事

推荐的一句话介绍：

> DeskPilot 是一个 Windows 本地优先的多 Agent 桌面助手。我用 Python/FastAPI 和显式任务状态图把自然语言目标转成受控工具调用，支持云端/本地模型切换、MCP 扩展、任务恢复、精确审批和可回放评测。

30 秒版本：

> 我没有把它做成“多个 prompt 互相聊天”的 Demo。Supervisor 只负责任务图，专业 Agent 只拿到必要工具，所有本地副作用都经过独立 Policy Engine 和 Tool Runner。复杂任务能暂停、审批、恢复和验证，模型/工具调用有 trace 和黄金任务集，可以量化成功率、安全、延迟和成本。

## 2. 招聘者应该一眼看到什么

仓库首页前两屏应展示：

1. 10～20 秒 GIF：输入任务 → 计划 → Agent 协作 → 审批 → 结果。
2. 一张清晰架构图。
3. 三个真实指标：黄金任务成功率、未授权副作用次数、P50/P95 延迟或平均成本。
4. 一键启动和离线安全 Demo。
5. 明确的安全边界与已知限制。

不要用大量营销词掩盖运行方式，也不要写未测量的“99.9%”“企业级”“完全安全”。

## 3. 推荐演示场景

### 3.1 主演示：求职资料研究助手（5～7 分钟）

用户请求：

> 在我授权的“求职资料”目录中找出最近三个月的 Java 简历和面试笔记，再搜索 5 个应届 Java 后端岗位的公开要求，提取共同技能，生成一份带文件引用和网页来源的 Markdown 查漏补缺报告。不要修改原文件。

演示价值：

- File Agent 按时间/类型检索。
- Knowledge Agent 解析文档并引用。
- Search/Browser Agent 并行收集外部资料。
- Supervisor 处理 DAG 和依赖。
- 本地/云端数据流清晰。
- 生成 artifact 并由 Verifier 检查来源数量。
- 只读任务无需多余审批。

### 3.2 安全演示：受控文件整理（2 分钟）

> 预览把测试目录中的 PDF 按月份移动到子目录；确认前不要修改。

先展示 dry-run manifest，再同意一次；在审批后人为修改一个文件，系统应使旧授权失效。这能直观展示 TOCTOU、防换参和审计，而不是只展示“弹了一个确认框”。

### 3.3 故障恢复演示（1～2 分钟）

运行多步骤任务后重启 API，恢复时跳过已验证步骤并继续。展示事件序号和幂等键，说明为什么不会重复执行非幂等动作。

### 3.4 离线后备演示

准备 Fake Model + 录制 trace + 测试网页/文件 fixture。面试现场网络或 API 不稳定时，仍能演示状态机、审批、工具、前端和回放；明确这是离线回放，不冒充实时模型。

## 4. 演示脚本结构

```text
0:00  痛点与目标
0:30  输入主任务，解释隐私模式
1:00  展示结构化计划和并发步骤
2:00  展开一个真实工具调用与证据
3:00  展示生成产物和引用
4:00  触发高风险审批，说明精确授权
5:00  打开 trace/评测面板
6:00  展示架构图、关键取舍与后续路线
```

演示过程中只讲三个核心取舍：确定性状态机、执行安全边界、可量化评测。其余细节留给问答。

## 5. 简历写法

指标未实际测量前，用占位符或描述性表述；达到后再替换。

### 5.1 三条版

- 设计并实现 Windows 本地优先多 Agent 助手，基于 Python、FastAPI、Vue 3 与状态图编排，将文件、系统、应用、浏览器、搜索能力统一为可恢复任务 DAG。
- 设计 OpenAI-compatible 模型网关与能力协商，支持云端/本地模型路由、结构化工具调用、调用预算、失败降级和 MCP 工具接入。
- 构建 Policy-as-Code 与独立 Tool Runner，对文件/进程/网络副作用实施风险分级、参数绑定审批、幂等恢复和事件审计；在 `[N]` 个黄金任务中达到 `[X]%` 成功率且未授权副作用为 0。

### 5.2 偏 Java 后端岗位的表达

- 使用领域模型和六边形架构拆分 API、应用用例、任务状态机、工具执行与基础设施，利用事件/outbox 保证任务状态和推送一致性。
- 针对长任务设计幂等键、超时、重试、熔断、资源锁、检查点与补偿动作，并通过 Fake Provider/轨迹回放实现确定性回归。
- 以 REST + WebSocket 构建前后端契约，OpenAPI/JSON Schema 生成 TypeScript 类型，Windows/Linux CI 分层验证。

## 6. Java 背景如何形成优势

虽然项目后端使用 Python，面试时可主动建立技术映射：

| Java/Spring 经验 | DeskPilot 对应 |
| --- | --- |
| Controller / Service / Repository | FastAPI interface / application use case / repository port |
| DTO + Bean Validation | Pydantic schema |
| CompletableFuture/Reactor | asyncio task、semaphore、cancellation |
| Spring StateMachine/状态模式 | Task/Step 显式状态机 |
| AOP/Micrometer | middleware + OpenTelemetry |
| Resilience4j | timeout、retry、circuit breaker |
| 事务 + Outbox | SQLite/PostgreSQL transaction + event outbox |
| SPI/插件机制 | Tool Registry、entry point、MCP |

重点不是说 Python 和 Java 完全相同，而是说明你理解语言之上的后端工程原则，并能快速跨栈实现。

## 7. 高频面试问题与回答要点

### 7.1 为什么要多 Agent，单 Agent 不行吗？

回答要点：不是为了角色数量。File/Computer/Browser 等能力域有不同工具、上下文和风险，拆分后能最小化工具暴露、独立测试和选择模型。单一明确的 R0 任务仍走快速路径，不强行多 Agent。

### 7.2 为什么没有把 LangGraph 作为核心 Runtime，这算重复造轮子吗？

回答要点：项目先认真评估了 LangGraph 的 durable execution、persistence、streaming 和 HITL，但现有 Runtime 已经把 PostgreSQL lease/fence、外部副作用 receipt/unknown/reconciliation、Approval、Verification 和跨进程恢复做成同一套领域协议。为获得一张图再引入 checkpoint/thread/node identity 会形成双真值。项目因此保留领域 Runtime，用服务端 `GraphViewProjection + Vue Flow + ELK.js` 做产品可视化，Mermaid 做脱敏导出；这是按真值边界选择组件，不是拒绝框架。若未来要迁移，必须先通过身份、崩溃注入、副作用、恢复和回滚等价性门禁。

### 7.3 如何保证 LLM 不执行危险命令？

回答要点：不能“保证模型永远不生成”。系统假设模型不可信：不提供通用 shell，工具严格 schema，Policy Engine 确定性决策，审批绑定最终参数，Runner 验签和资源版本，OS 权限再限制。

### 7.4 网页提示注入怎么办？

回答要点：网页是带来源的不可信数据，不能改变任务目标和权限；工具最小暴露，外发/写操作独立审批，Policy 不读取网页的“授权”。用对抗网页做回归测试。

### 7.5 任务中断如何恢复？

回答要点：任务状态和事件持久化；恢复时 running 步骤先 reconciliation。幂等步骤可重试，非幂等步骤先查后置状态，无法确认则进入 unknown 等用户处理，不盲重试。

### 7.6 OpenAI-compatible 为什么还要多个 adapter？

回答要点：兼容通常只覆盖部分端点。工具调用、严格 JSON、流式、视觉和错误码不同，因此先能力探测，再使用共同子集或原生 adapter；隐私不足时不能静默换 Provider。

### 7.7 为什么不用微服务、Kafka、Kubernetes？

回答要点：这是单用户本地系统，核心约束是 OS 安全和长任务可靠性，不是吞吐。单机多进程 + SQLite 更可交付；通过 port、事件和 Runner 协议预留未来分布式演进。

### 7.8 如何衡量 Agent 是否变好？

回答要点：固定黄金任务和 fixture，优先用文件哈希、引用、PID 等确定性 grader；分别统计成功、安全、延迟、Token/费用。录制 trace 离线回放，prompt/model 版本独立对比。

### 7.9 如何处理并发和资源冲突？

回答要点：DAG 中无依赖步骤可并行，但调度器根据文件/浏览器/系统设置资源锁限制；Provider 有 RPM/TPM 信号量；审批前不执行副作用。

### 7.10 最大限制是什么？

诚实回答：GUI 自动化对界面变化敏感，本地小模型工具调用不稳定，Python 用户态隔离不是强安全沙箱，跨端远控不在 MVP。项目用 DOM 优先、能力协商、独立 Runner 和明确范围降低风险。

## 8. 可形成的 STAR 故事

### 8.1 可靠性

- Situation：模型/网络可能在长任务中断。
- Task：保证恢复且不重复副作用。
- Action：事件持久化、幂等键、reconciliation、unknown 状态、故障注入。
- Result：用实测的恢复成功率/无重复写次数说明。

### 8.2 安全

- Situation：网页提示注入可诱导桌面 Agent 外发文件。
- Task：让模型被攻击时执行面仍安全。
- Action：信任标签、最小工具集、Policy-as-Code、参数绑定审批、对抗测试。
- Result：报告 `[N]` 个对抗 case、违规执行 0 次。

### 8.3 模型兼容

- Situation：云端和 Ollama 的工具/JSON 支持不一致。
- Task：在不污染业务层的情况下切换。
- Action：Provider port、能力档案、路由、降级、contract test。
- Result：说明验证过的 Provider 数、同一黄金任务差异。

## 10. 竞争力提升顺序

如果时间有限，最有价值的投入顺序是：

1. 真实端到端闭环与稳定演示。
2. 权限/审批/提示注入防护。
3. 任务恢复和轨迹回放。
4. 黄金任务指标。
5. 本地/云端模型切换。
6. MCP 扩展。
7. UI 视觉打磨。
8. 视觉电脑操作、远程控制等高成本功能。

前六项更能证明后端与 Agent 工程能力；仅做漂亮 UI 和大量 Agent 头像，竞争力有限。

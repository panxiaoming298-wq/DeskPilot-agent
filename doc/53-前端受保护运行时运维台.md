# 阶段 53：前端受保护运行时运维台

## 1. 本阶段目标

阶段 50 已建立 graph-control、cluster admission、ready projection 与 Outbox/Inbox 的统一受保护 operations API；阶段 51～52 又补齐 PostgreSQL 性能和故障门禁。本阶段开发时尚未执行专用 PostgreSQL 门禁，因此只完成已有后端契约的安全前端入口；后续阶段 54 已在 Docker 真库完成复验：

- 同屏展示四域数据库时间指标、稳定告警码和有界脱敏样本；
- 显式触发 metrics sample，并展示 append-only hash-chain 审计；
- 对 bounded retention 和 DLQ requeue 提供二次确认、提交锁与持久化幂等重试语义；
- 不展示 graph control reason、Outbox payload/error 原文、Tool 参数或凭据。

## 2. 类型与 API 契约

`frontend/src/types.ts` 镜像 operations v1 的公开读模型，包括四域 metrics、sample、alert、audit、retention result 和 requeue result。它不新增可写 graph/admission/ready 字段，也不接受原始 payload 或 error detail。

`frontend/src/api.ts` 新增五个受认证调用：

```text
GET  /api/v1/operations/effect-runtime
GET  /api/v1/operations/effect-runtime/audit
POST /api/v1/operations/effect-runtime:sample
POST /api/v1/operations/effect-runtime:run-retention
POST /api/v1/operations/outbox/{message_id}:requeue
```

所有请求继续通过本地 session Bearer 和 `X-DeskPilot-Client`；浏览器同源写请求由既有 Fetch Metadata/Origin 边界保护。只有 retention/requeue 携带 `Idempotency-Key`，metrics sample 不在传输失败后自动重试。

## 3. 服务端真值状态管理

`useEffectRuntimeOperations` 不做乐观 mutation：

1. 初始化并发读取 snapshot 与 audit page；旧 generation 的迟到响应不会覆盖新读取；
2. metrics sample 只在服务端返回后替换 snapshot、合并 audit event；
3. retention 根据规范化保留天数生成 key，传输失败后保留；只有用户再次显式确认相同请求时才复用，正文变化会生成新 key；
4. requeue 只接受当前 snapshot 中的 dead-letter message，响应 `message_id` 必须精确匹配；错配响应被忽略且保留原重试 key；
5. 服务端确认写入后再重新读取 snapshot/audit。若刷新失败，UI 明确提示“写入已确认但刷新失败”，不会把已提交操作重新 POST。

这使前端保持与后端相同的 durable receipt 语义：请求结果不明时不猜测，人工重试复用同一幂等身份，成功状态只来自服务端。

## 4. 四域运维视图

侧栏新增“运行时运维”入口。页面显示：

- graph-control actionable/unrouted/expired claim 和 fenced mailbox 样本；
- cluster admission live pending/granted、scheduler revision、grant sequence 与 ticket fence；
- ready projection node/ready/drift/rebuild 指标和 content digest；
- Outbox pending/in-flight/published/DLQ、Inbox receipt 和 delivery fence；
- stable alert code/severity/count；
- audit sequence、action、actor、event digest 和 previous digest。

摘要只显示缩略值，但浏览器内仍只接收后端公开的 64 位 digest，不接收对应敏感正文。页面无自动修复、自动 requeue 或后台轮询副作用。

## 5. 受保护写交互

### 5.1 Retention

用户先输入 1～3650 天，再进入 `alertdialog` 二次确认。确认文案明确：只清理安全终态派生记录，DLQ、TaskEvent、active/blocked graph 不会删除；清单摘要、审计 head 与删除由后端同事务提交。提交期间其他运维动作锁定。

### 5.2 DLQ requeue

只有 `state=dead_lettered` 的有界样本显示按钮。二次确认说明只重置单条消息并提升 delivery fence，不显示或改写 payload。前端不会本地把记录改成 pending；提交后重新读取数据库真值。

### 5.3 Metrics sample

采样会追加审计，因此只由用户显式点击。它没有自动定时 POST 或传输层自动重放；后端 scheduler 的周期采样仍由服务端自己管理。

## 6. 自动化验证

新增 API、composable、组件和 App 导航覆盖：

- operations 路径、query、Bearer/client header 与 Idempotency-Key 边界；
- 四域 snapshot/audit 初始化和 sample 合并；
- retention 网络失败后的人工同键重试；
- 非当前 DLQ 拒绝、响应身份错配拒绝和同键重试；
- retention/requeue 二次确认与提交前零 mutation；
- UI 不渲染 payload/error 原文，App 可进入独立运维页。

## 7. 已知边界与下一步

1. audit 当前读取有界首批记录并显示 `has_more`，尚无完整游标浏览、链验证可视化或签名导出。
2. 告警仅在页面读取时显示，尚无桌面通知、静默/确认状态或外部指标/告警通道。
3. operations 页面不是集群管理写面；它刻意不提供 graph-control/admission/ready 的任意修改或修复按钮。
4. 阶段 51～52 的 PostgreSQL 门禁已在后续阶段 54 使用专用 Docker 测试库执行通过；server restart/failover、TCP 分区仍未覆盖。
5. 外部 broker 仍未接入，响应丢失、at-least-once 重投、Inbox 去重和旧 publisher fence 仍需真实环境演练。

下一阶段入口：**保存可比较的 PostgreSQL JSON plan/BUFFERS/时延基线，继续建设 audit 游标/导出与告警通知，并准备真实 broker adapter 和显式选入的 OS/网络故障门禁。所有写路径继续保持服务端真值、二次确认、幂等 receipt、delivery fence 与 unknown 不猜测语义。**

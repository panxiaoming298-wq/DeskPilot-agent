# 阶段 102：服务器裁决测试结果条件边

## 1. 本阶段结论

阶段 102 修复了动态 Agent DAG 的一个真实语义缺口：阶段 98 的固定 Python/Node Tester 即使返回 `failed`，其执行记录仍可能作为“已完成并结构验证”的结果进入普通 verified 依赖；拓扑只能表达“上游结束”，不能表达“上游测试通过”。本阶段新增服务器绑定的 `test_passed` 条件边，使下游节点只有在服务器读取并裁决固定测试或图内 Patch/Test 的真实结果后才会变为 ready。

```text
Coordinator proposes dependency + test_passed predicate
                         ↓
Supervisor binds exact source node / target node / predicate
                         ↓
Tester or Patch/Test emits typed ResultRef
                         ↓
Server reads persisted result status and seals a decision
                 ┌───────┴────────┐
             matched=true      matched=false
                 ↓                 ↓
       unlock downstream      fail graph and fence siblings
```

模型只提议条件的拓扑位置，不能提交裁决结果。浏览器、Repair Advice、Memory、Summary、旧 ResultRef 或普通 verified 状态也不能把失败测试改判为通过。

## 2. Graph v7 与严格条件提议

`AgentTaskGraphNodeProposal` 新增有限 `conditions`，当前唯一谓词为：

```json
{
  "source_local_key": "python_test",
  "predicate": "test_passed"
}
```

服务器只接受条件来源同时出现在该节点 `dependencies` 中，并拒绝重复 source。对固定 Python 测试、固定 Node 测试和图内 Patch/Test 节点的每条出边，Supervisor 强制要求恰好一个 `test_passed` 条件；缺少条件会在封图和执行前失败，不能退回普通 verified edge。

Task Contract 通过 `server_adjudicated_test_conditions_v1` 明确授权这一协议。旧 graph v1～v6 保持摘要兼容且不允许条件；只有新 `deskpilot.agent-task-graph.v7` 能封装条件 manifest。

## 3. 服务器绑定与持久证明

Supervisor 将模型的 local key 解析为不可变 `BoundAgentTaskGraphCondition`，绑定：

- graph、source local key 和精确 source node ID；
- 固定 `test_passed` 谓词；
- 内容寻址 condition digest。

执行边新增 `server_condition` requirement，并同时保存 condition manifest/digest 和后续 decision manifest/digest。普通 `verified` edge 的四个条件字段必须全部为空；条件边缺字段、字段混用或摘要漂移都会 fail closed。

`AgentTaskGraphConditionDecision` 由服务器生成，绑定 graph/source/target、谓词、实际结果状态、精确 ResultRef digest、`matched` 和 decision digest。`matched` 只能由固定规则得出：`passed` 或 `verified` 为真，`failed`、`error`、`test_failed` 和 `test_error` 为假。

## 4. 调度与失败收敛

通用 verified-edge reducer 现在同时验证普通边和条件边。目标节点变为 ready 前必须满足：

- 所有 source execution node 已 verified；
- 所有普通边不存在条件状态；
- 所有条件边的绑定和裁决完整、摘要正确且与 exact edge/ResultRef 一致；
- 每个服务器裁决均为 matched。

条件尚未裁决时，下游继续 pending。裁决为 false 时，系统不会把失败当成等待或可重试成功，而是将 graph、parent node、parent invocation、execution run 和 Turn Route 收敛为失败，稳定错误码为 `AGENT_GRAPH_TEST_CONDITION_NOT_MET`；未开始的图节点被取消，在途并行 sibling 被 fencing。Workbench 的并发 wave 使用异常聚合后重读服务器投影，只把这一种已经证明的条件失败显示为正常阻断，其他 proof/binding 异常仍返回 409。

## 5. Workbench 与前端

Workbench 动态图节点新增：

- 服务器绑定的 condition manifest；
- persisted condition decision；
- source、predicate、matched 状态和证明摘要。

前端对含条件的图显示 `SERVER-CONDITIONAL`，节点显示 `CONDITION <source>.TEST_PASSED` 以及 `PASSED`、`BLOCKED` 或 `WAITING`。这些字段只用于解释服务器真值，前端不提交条件结果，也不能解锁节点。

## 6. 正向、负向与篡改语义

正向组合图已覆盖 directory、Python test、Node test 和 join：两个 Tester 都由服务器判为 passed 后，join 才领取并产生最终输出。负向闭环使用真实返回 `failed` 的固定 Python 测试运行时，验证：

- Tester 结果和 ResultRef 如实保存，条件 decision 为 false；
- join 保持未执行并被取消，最终目录输出没有产生；
- graph/Route/Run 失败而不是 false-success；
- 篡改 decision manifest 或 digest 后，Workbench 读取返回 409；
- Coordinator 省略测试条件时，图在执行测试前即被拒绝。

阶段 101 的 Patch/Approval 暂停、确认、原子提交与 `patch_test` 续接保持兼容。条件边不授予写权限，也不创建第二个 Patch；未来任何新 Patch generation 仍必须建立新的 Workspace manifest 并取得新的精确确认。

## 9. 与 Codex/Marvis 的距离

系统现在能在持续对话产生的动态异构 DAG 中，把“测试通过”表达成服务器可证明的控制流条件，而不是依赖模型文本或任务完成状态猜测。动态图具备了提议、服务器封图、类型化数据流、批准式写入、固定测试、条件裁决、并行 fencing 和可解释 Workbench 投影的连续闭环。

当前仍不是任意自主编码系统。谓词固定为 `test_passed`，false 分支只做安全失败收敛；尚未在同一任务内根据失败快照生成新的节点级 Plan generation，也没有多个连续 Patch/Approval 节点、自由 Shell、依赖安装、目录创建/删除/覆盖、登录态浏览器或 live-model/Judge-human 校准。下一阶段应优先把 false decision 转成新的不可变 Plan generation，同时继续证明每个新 Patch 都需要独立授权。

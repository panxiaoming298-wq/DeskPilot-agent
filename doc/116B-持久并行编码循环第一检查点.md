# 阶段 116B：持久并行编码循环第一检查点

## 1. 检查点结论

116B 第一个代码检查点已落地：新的 `workspace_coding_loop` planner-only Route 在同一持久 TaskLoop 中走通两个独立 Workspace Reader 并行调查、双 verified ResultRef join、精确双文件 Patch 确认与写入、服务器固定 Python/Node Test、已知失败回执、一次有界 Repair、独立 final acceptance 和结构化 Delivery 证据持久化。

这个检查点已证明 `Delegate → Patch → Test → Repair → Verify → Deliver` 的 LOCAL-only/Fake 运行时纵切，但不标记整个 116B 完成。同会话用户修订的新 generation/lease fencing、真实版本化 Patch Planner 模型 Handoff 和公开交付投影仍是下一检查点。

## 2. 固定 Contract 与 DAG

Route 只接受来自用户持久消息的两个精确 Reader 路径、一份恰好两项的 `changes_json`、项目路径、单一测试路径和服务器固定的 Python/Node 生态。路径必须是安全相对路径，两个 Patch 文件必须与两个 Reader 完全一致且位于项目内。模型不能提供 executable、argv、cwd、env、Shell、依赖安装、Git 写入或 push 指令。

服务器编译的 DAG 为：

```text
inspect_primary    inspect_secondary
        \              /
         +-- verified join --+
                    apply_patch
                         |
                  run_fixed_test
                         |
                 final_acceptance
                         |
                      delivery
```

- 两个 Reader 绑定不同 local key、精确 node ID、Workspace path、`builtin.workspace_reader` Contract/Handoff/Invocation 和只读 Capability；
- reducer 只会为同一 proof-checked snapshot 中恰好两个 canonical ready Agent node 生成 `execute_agent_batch`，候选执行使用 `asyncio.gather` 并行；
- Patch node 必须同时携带两个已验证依赖 ResultRef，但 ResultRef 不能生成新路径或新写权；
- `task_loop_deferred` 绑定使 planner-only 单 Offer 只作为 TaskLoop 授权输入，不会先占用 generation-1 active Plan。

## 3. 执行、失败与恢复

- 并行 Reader 候选和共享 Agent Result 持久后，可在新 `TaskLoopAgentRuntime`/新 Coordinator 实例中按精确 node 恢复验证；已验证 Reader 不重跑。
- Patch 仍使用现有 preview/confirmation digest/一次性 approval 边界；写入后保存每文件 backup path、previous/current version digest 和 receipt digest。
- `workspace_check`/Python Test/Node Test/Command Profile 的非 `passed` 输出现在都形成独立 verified failure ResultRef 和不可变失败回执，Attempt/Node 标记 `failed`，不解锁后继。
- 固定测试节点允许一次已知失败后的新 Attempt；最终验收只使用唯一 `passed` ResultRef，失败历史仍保留。
- outcome unknown/running/过期租约的写操作继续遵循 `NO_AUTOMATIC_REPLAY`，没有被改成自动 Repair。

## 4. 结构化交付证据

`0058_workspace_coding_deliveries` 为每个成功 coding execution 保存一条内容寻址、不可变的证据摘要，不引入第二套执行状态机。Delivery manifest 包含：

- 两个 Reader 的路径、文件版本和 ResultRef digest；
- 结构化 old/new diff、变更文件清单、Patch ResultRef/receipt digest；
- 执行过的测试、exit code、结果和验证 digest；
- 失败/Repair 历史与失败回执 digest；
- 剩余风险 `local_fake_model_quality_unproven`/`git_commit_not_created`；
- 逐文件 backup 可回滚点与版本 digest。

Delivery 前会重验 runnable binding 集合、ResultRef Schema/摘要、producer Attempt、Reader/Patch 路径一致性、唯一成功测试和失败回执。已有记录只允许相同内容幂等重读；有数据 downgrade 被拒绝。

# 阶段 80：隔离多文件补丁与一次确认提交

阶段 79 只能在一个文件中完成一次精确替换。阶段 80 把这条安全边界扩展为结构化多文件补丁：用户在一条对话指令中提供 2–8 个不同文件的精确替换，系统先在内部隔离副本中建立 before/after 与内容寻址清单，用户检查全部 diff 后只需确认一次。

本阶段已实现。它让 DeskPilot 可以完成一个最小的跨文件代码修改，但仍未开放自由 Shell、动态 Python、正则批量替换、新建、删除、重命名、目录级写入或任意覆盖。

## 1. 固定 Route 语法与能力声明

首版语法为：

```text
批量修改工作区文件：在工作区文件 a.md 中把 "旧文本" 替换为 "新文本"；在工作区文件 b.py 中把 "before" 替换为 "after"
```

`workspace_patch_bundle@1` 是 R1 Capability，只接受 2–8 项、路径不重复、每项旧文本非空且恰好出现一次的指令。解析结果以规范 JSON 存入 Route 参数，并继续绑定 classifier version、原消息摘要、Route manifest、Capability、Contract、Plan 和 Run。

任何语法歧义、路径重复、项数超限、零次/多次匹配或文件边界违规都 fail closed，不把请求猜成另一种写入。

## 2. 隔离补丁 Artifact

预览阶段对每个文件建立：

- 规范相对路径；
- 原文件稳定版本摘要和内容摘要；
- 拟写内容摘要与字节数；
- 旧文本、新文本与单项 change digest。

系统在 `artifact_workspace_root/.deskpilot-workspace-patches/<task-digest>/` 下使用独占创建写入 `before/`、`after/` 和规范 `manifest.json`，然后使用同文件系统重命名公布完整副本。目录名由 Task ID 摘要派生，不接受用户路径。内部目录使用点前缀，Conversation Workspace 路径解析器显式拒绝所有点前缀路径段，避免隔离证据被对话文件能力读取或修改。

`deskpilot.workspace-patch-preview.v1` 绑定全部 change digest、staging workspace ref、manifest digest、总字节数和 confirmation digest。重试预览时，只有现有隔离目录与同一清单和全部 before/after 字节完全一致才会复用。

## 3. 一次确认与提交

对话流中的审批卡同时展示：

- 要做什么：准备替换的文件数和精确匹配数；
- 影响什么：拟写总字节数和逐文件备份政策；
- 凭什么：隔离 manifest digest 与可直达的逐文件 diff；
- 拒绝、改一下和确认全部替换三个动作。

确认时先重验隔离清单与全部 before/after，再对所有目标做一次全量版本预检。只有全部未提交文件仍符合预览，或已提交文件可由新内容+旧版本备份确定恢复，才开始写入。

每项提交复用阶段 79 的 Windows `ReplaceFileW` 原子替换、独立安全备份与结果复核。子提交 ID 由补丁 Task ID+项序号派生，使各文件备份名稳定且可恢复。

## 4. 多文件非原子边界

普通文件系统没有“一次原子替换 N 个文件”的原语。阶段 80 不隐藏这个边界：

1. 写入前先预检全部文件，常规版本漂移在任何写入前就被拒绝。
2. 提交过程中如仍遭遇外部编辑竞争或 OS 故障，已完成项不伪装成整体成功。
3. `deskpilot.workspace-patch-receipt.v1` 用 `committed` 或 `partial` 明确标记整体状态。
4. `partial` 回执列出所有已提交项及其安全备份、首个未完成路径和稳定错误码，Route/Run 标记为 failed/blocked。
5. 若进程在数据库完成前中断，重试会先根据逐项备份识别已跨过的原子边界，然后从首个未提交项继续。

本阶段不做自动回滚：补偿写入会引入新的外部效果和竞争窗口，且可能覆盖用户在部分完成后的新编辑。当前选择是保留实际事实、保留每项备份并要求人工处置，而不是猜测恢复。

## 5. 验收覆盖

自动化验收覆盖：

1. 固定对话语法解析与规范参数摘要；
2. 2–8 项与重复路径边界；
3. 预览零原文件效果；
4. before/after/manifest 隔离副本内容复核；
5. 对话文件能力不能穿透点前缀内部目录；
6. 任一文件版本漂移时全部零写入；
7. 成功一次确认后逐项原子替换、独立备份与完整回执；
8. 同一补丁重复提交返回同一事实；
9. 中途失败生成 partial 回执，后续重试可安全续提；
10. 前端在对话流中展示逐文件 diff，不进入安全自动推进；
11. 错误 confirmation digest 不调用文件提交；
12. 成功和 partial 均展示逐项备份与不可变补丁回执。

本阶段不需要数据库迁移，复用 `0037_turn_routes` 的 Route result manifest 保存预览、完整回执和 partial 回执。

最终验证：后端完整回归在阶段 80 主实现完成后收集 501 项，结果为 `489 passed, 12 skipped, 1 warning`，退出码 0；最后增加 partial API 持久化和内部路径硬化后，当前收集数为 502，阶段 80 相关最新 19 项定向用例再次通过。Ruff 全仓通过，mypy 通过 215 个生产源码，Alembic 保持单一 `0037_turn_routes` head 且 autogenerate check 无新操作，`uv lock --check` 通过。

前端 22 个测试文件/148 项、Vue type-check 和 production build 通过；工作台与八状态审批预览的 `finesse-ui` 静态检测为 `p0: 0`，`git diff --check` 通过。按界面技能的组件范围约束，本次没有自行打开用户页面做视觉断言；八状态可在 `frontend/src/components/WorkspaceApproval.preview.html` 中人工快速复核。

## 6. 下一阶段

下一阶段应优先增加只读目录列表和受控测试命令，而不是直接开放自由 Shell。测试命令应使用固定 allowlist、隔离子进程、时间/输出上限、默认断网、脱敏日志和只读工作区副本。等“读取→补丁→验证”形成完整闭环后，再评估更广的代码执行能力。

# 阶段 44：条件边与内容寻址分支决策证明

## 1. 本阶段目标

阶段 43 已把受信 v2 DAG 的逐节点 Tool 账本、并行 Runner 和反向补偿 wave 接通，但图定义只有无条件 `success` edge。阶段 44 增加一个可恢复的条件分支原语：分支选择必须由受信应用 resolver 产生、作为数据库事实提交，并被后续 ready-set、claim、skip reducer 和查询证明共同引用。

本阶段仍不允许模型直接改写图、决定授权或把自然语言结果当作执行许可。

## 2. 条件边定义

`EffectDagNodeDefinition.conditional_depends_on` 接受不可变的 `EffectDagBranchCondition`：

```text
predecessor_key + decision_key + expected_outcome
```

创建 DAG 时会同时持久化：

- 正向 `conditional` edge，包含 `decision_key/expected_outcome`；
- 对应的反向 `compensation_order` edge；
- `effect_graph.created` 中的脱敏条件定义。

普通 `success` edge 的内容寻址 ID 保持不变。条件前驱和普通前驱共同参与依赖存在性、重复前驱和环检测；同一目标不能把同一前驱同时声明为条件与无条件依赖。

## 3. 分支决策是不可变数据库事实

受信 resolver 只能在以下条件同时成立时写入决策：

1. 持有有效 graph lease 和 fencing token；
2. graph 仍为 `active` 且没有 cancel intent；
3. source node 已有持久化 `succeeded` 终态；
4. `decision_key/outcome` 已由图上的条件边声明；
5. 提供 64 位 `evidence_digest`，原始判定材料不进入脱敏 effect graph。

`tool_effect_branch_decisions` 保存 source node revision/event sequence、decision/outcome、evidence digest、proof digest 和原子 task event。证明材料按 canonical JSON 计算 SHA-256：

```text
schema + graph + source identity/status/revision/event
+ decision key/outcome + evidence digest
+ 该 decision key 的全部条件边定义
```

`decision_id = tbd_<proof_digest>`，因此决策本身是内容寻址的。相同 outcome/evidence 的重试直接返回原记录，不增加 graph revision 或事件；试图改写 outcome/evidence 会得到稳定冲突。读取 graph 或计算 ready-set 时会重新计算摘要，记录或边元数据被篡改都会 fail closed。

## 4. Dispatcher、ready-set 与恢复

`EffectDagDispatcher` 新增可选的 `EffectBranchDecisionResolver` 受信边界。当图仍 active、当前没有 ready node，且发现“source 已成功但 decision 尚未落库”的分支点时，dispatcher：

1. 向 resolver 提供 source node、decision key 和图中声明的 outcome 集合；
2. 将 resolver 返回的 outcome/evidence digest 交给带 graph fence 的事务命令；
3. 先持久化内容寻址 decision，再运行 reducer 和下一轮 ready-set；
4. resolver 缺失或返回 `None` 时保持图等待，不猜测默认分支。

条件目标只有在全部前驱 `succeeded` 且对应 decision outcome 精确匹配时才进入 ready-set。`EffectReadyNodeProof` 现在同时包含前驱 revision/event 证明和匹配的 `EffectBranchDecisionProof`，ready digest 升为 `deskpilot.effect-ready-set.v2`。

决策提交会推进 graph revision/event sequence，因此提交前生成的 ready proof 立即失效。重启后不依赖 dispatcher 内存：新实例从数据库重读 edge/decision，重新得到相同的选中路径和内容证明。

## 5. Skip、终态与补偿

Reducer 对条件边使用三值语义：

| 条件状态 | 目标节点行为 |
| --- | --- |
| 尚无 decision | 保持 `pending`，等待受信判定 |
| decision 与 expected outcome 匹配 | 允许进入后续 ready-set |
| decision 已存在但不匹配 | `skipped`，原因 `branch_not_selected` |
| 条件前驱 failed/unknown/skipped/cancelled | 按依赖阻断传播 `skipped` |

未选分支的普通后继会继续通过既有 reducer 传播 `skipped`。当所有节点均为 `succeeded/skipped` 时，graph 归约为 `succeeded`。

补偿计划把 `conditional` edge 与 `success` edge 同等视为正向依赖；只有实际成功并产生效果的选中节点进入补偿集合，仍按 reverse-topological 顺序先补偿分支下游、再补偿 source。

## 8. 已知边界与下一步

1. 条件边和 resolver 已进入通用 v2 dispatcher，但当前公开受信业务请求 `file_move_dag` 仍只生成 success edge；后续新增具体条件业务计划时，必须由应用注册 resolver 和证据投影，不能接受模型自由分支或原始敏感证据落图。
2. graph cancel intent 已阻止新 claim，但仍未向已在途 Runner call 广播 cancel IPC；下一阶段实现 cancel 控制面并保持 prepare/commit/unknown 与 graph/node fence 语义。
3. 并发上限仍是单图固定值；尚需全局公平性、每图/每 Tool 配额、ready-set 分页、backpressure 和大图压测。
4. Outbox DLQ/requeue/cleanup 仍只有应用原语；尚需受保护的运维 API/UI、retention scheduler、指标审计。
5. PostgreSQL 原生 claim 已通过方言编译，仍需真实双实例、进程杀死、超时和网络分区故障注入。

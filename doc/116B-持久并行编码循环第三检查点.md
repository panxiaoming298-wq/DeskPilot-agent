# 阶段 116B：持久并行编码循环第三检查点

## 1. 检查点结论

116B 第三个代码检查点已落地：`workspace_coding_loop` 在两个 Reader 之前新增一个真实、持久、LOCAL-only 的 `builtin.workspace_coordinator@1.1.0` Model Turn/Handoff。Coordinator 只能确认服务器从已封存 composite Plan 重建出的六节点编码子图，不能创建或修改路径、Capability、依赖、输入来源、预算、工具或权限。确认通过后签发独立 `coordination_plan` ResultRef，原 TaskLoop 才解锁两个 Reader；没有新增第二套 DAG 或步骤状态机。

本检查点完成了第二检查点指定的受约束 Dynamic Coordinator 纵切，但没有把整个 116B 标记完成。固定双文件任务尚未推广为更真实的有界多文件仓库循环，Git 仍只有 `status/diff/log` 只读能力；branch/commit receipt、依赖变更、自由 Shell、自动 push、真实 cloud 模型质量与生产激活均未开放。

## 2. 固定图与权限边界

当前固定执行顺序为：

```text
                  coordinate_coding
                         |
             +-----------+-----------+
             |                       |
      inspect_primary          inspect_secondary
             |                       |
   plan_primary_patch       plan_secondary_patch
             \                       /
              +---- verified join ---+
                         |
                    apply_patch
                         |
                  run_fixed_test
                         |
                 final_acceptance
                         |
                      delivery
```

- Coordinator 绑定新注册的只读 `workspace.dynamic.coordinate.v1` Capability Pack、exact Agent/Prompt digest 和一个模型调用预算；工具调用与 handoff 预算均为 0。
- 服务器 Offer 恰好包含 `inspect_primary`、`inspect_secondary`、两个 Patch Planner、`apply_patch` 与 `run_fixed_test` 六个完整节点；节点目标、Capability、输入来源/绑定槽、依赖和 `PlanNodeBudget` 均来自已激活 Plan。
- 模型必须返回同一六节点图和唯一输出节点 `run_fixed_test`。最终验收与 Delivery 不交给模型选择，仍由服务器 Reducer 独立执行。
- Reader 在 TaskLoop 中恰好只依赖 Coordinator。Coordinator ResultRef 不作为 Patch 写入输入；Patch 仍只消费两个独立验证的 `patch_proposal` ResultRef，并继续等待用户对 exact staging digest 的确认。
- Fake Provider 只逐项回显服务器提供的固定节点，用于 LOCAL/offline 结构验收；它不能推导新节点、路径或命令。

## 3. 持久 ModelTurn 与验证链

Coordinator 复用现有持久执行结构：

1. TaskLoop claim 创建 exact Handoff、Invocation 和 fenced Attempt；
2. `AgentModelLoopRuntime` 持久化 ModelTurn 与 dispatch attempt；
3. Dynamic Coordinator 决策必须通过严格 `AgentProposeTaskGraphDecision` Schema；
4. Runtime 将返回节点与服务器重建图逐项比较，随后以 graph binding ID 接受 Decision；
5. `AgentOutputResult` 绑定 request/response/schema、Decision 和 graph digest；
6. 独立 `AgentVerifiedResultBridge` 重载 ModelTurn、Decision、Agent Result、source-step/composite Plan/node proof 后签发 `COORDINATION_PLAN` ResultRef；
7. `mark_verified_and_unlock` 仍是唯一后继解锁入口。

进程重启后从同一 ModelTurn/Decision/ResultRef 恢复，不再次调用模型。真正的 dispatch outcome unknown 继续使用 `NO_AUTOMATIC_REPLAY` 语义。本检查点没有新增数据库表或列：ResultRef kind 存于既有字符串列，证据进入既有内容寻址 JSON manifest，因此 Alembic head 保持 `0059_workspace_coding_amendments`。

## 4. 篡改与失败收敛

- 即使模型响应满足 JSON Schema 且仍是合法 DAG，只要任一 objective、Capability、依赖、输入槽、预算或输出节点与服务器图不同，就以 `TASK_LOOP_COORDINATOR_GRAPH_REJECTED` 拒绝。
- 确定性越权决策会把 ModelTurn 标记为 failed，并在同一收敛流程中终止 Invocation、TaskLoop Attempt、Node 和 Run；两个 Reader 保持 pending，不生成 ResultRef，也不进入自动重试。
- 同一终止流程也补齐了 Patch Planner 返回 Schema 合法但越过精确 replacement Offer 时遗留 running lease 的边界。
- source Contract/Plan、composite Plan、node spec、Agent/Prompt、request/response、Decision、Agent Result、graph 和 ResultRef 摘要均在恢复/bridge/Delivery 路径复验；任一 manifest 单独漂移都会 fail closed。

# 阶段 103：测试失败驱动新计划代与逐补丁再批准

## 1. 本阶段结论

阶段 103 把阶段 102 的 `test_passed=false` 从“只会安全失败”提升为一次由用户显式触发的修复换代。动态图内 Patch/Test 写入已经发生但固定测试未通过时，服务器先保存类型化失败结果和 false condition decision；系统不会自动重试，也不会把旧补丁、Repair Advice 或失败结果解释为新的写权限。只有用户选择“生成新计划代”后，才会在同一 Task/Contract 下原子创建 generation 2。

```text
generation 1 Patch approval
           ↓ exact confirmation
workspace write + fixed test failed
           ↓
patch_test ResultRef(test_failed)
           ↓ server test_passed decision=false
graph / Run / Route failed
           ↓ no automatic replan
user explicitly requests a new generation
           ↓
immutable Replan v3 + generation 2 Plan/Run
           ↓
read current workspace → new Patch manifest
           ↓ new exact confirmation
second approval → write → fixed test → condition decision
```

因此，“允许继续修复”只授予一次 execution-control 换代，不授予文件写能力。generation 2 的 Patch 仍必须重新预演，并获得绑定新内容摘要的独立批准。

## 2. 失败结果现在进入条件真值链

阶段 101 的图内 Patch/Test 在测试失败时会直接调用失败收敛，阶段 102 的 `test_passed` 条件边因而拿不到可裁决的 `patch_test` ResultRef。本阶段修正了这条路径：

- Patch 已提交且固定测试返回 `failed`/`error` 时，组合结果仍以 `test_failed`/`test_error` 如实持久化；
- 当前 Patch 节点完成结构验证并生成 exact `patch_test` ResultRef；
- Supervisor 读取持久结果，在 `server_condition` edge 上保存 `matched=false` decision；
- false decision 随后以稳定错误 `AGENT_GRAPH_TEST_CONDITION_NOT_MET` 收敛 graph、Parent、Run 和 Route，并取消未执行节点；
- 旧 graph v1～v6 仍采用原失败语义，不能借新规则接受非成功结果。

这里的“结构验证完成”不等于“测试通过”。是否允许下游运行仍只取决于服务器 condition decision。

## 3. Replan v3 与失败快照 v2

新增的条件失败 Replan 使用：

- `deskpilot.agent-replan-failure-snapshot.v2`；
- `deskpilot.agent-replan-repair-advice.v2`；
- `deskpilot.agent-replan.v3`。

失败快照绑定原 Task、generation 1 Plan/Run/Contract、Route 参数摘要、稳定错误码，以及一个或多个经过重验的 false condition decision digest。该路径没有失败 Model Turn，因此 `failed_model_turn_ids` 必须为空；旧目录协议错误 Replan 仍使用 v1 snapshot 并要求失败 Turn。

Repair Advice 的固定策略为 `propose_fresh_patch_after_failed_test`，`granted_capability_ids` 必须为空。服务器只可提供仍可逐项重验的只读 ResultRef；失败的 `patch_test` ResultRef 被明确排除，不能导入新图、不能变成 approval，也不能授权重放旧写入。

读取 Replan 谱系时会重新计算 condition decision 集、failure snapshot、Repair Advice sources 和两代 Plan/Run 绑定。decision manifest/digest、旧 ResultRef 或 lineage 任一漂移都会以 `PLANNING_PROOF_REJECTED` fail closed。

## 4. 用户控制与非自动边界

动态 Patch 条件失败后，Workbench 会公开 `replan_failed_execution`，但服务器后台推进器和前端观察循环都故意忽略这一动作。Task Contract 同时约束：

- `no_automatic_replan_after_workspace_write_v1`；
- `one_user_requested_condition_failure_replan_v1`；
- `fresh_confirmation_after_replan_v1`；
- `fresh_user_confirmation_per_patch_v1`。

用户未明确请求时，任务保持 blocked。用户请求后只允许 generation 1 → 2；重复换代、第二代再次失败后的自动重试，以及非白名单 Route 的换代全部拒绝。

前端以独立的人类动作卡展示 `TEST CONDITION BLOCKED`、false decision 摘要、旧写入事实和“生成新计划代”按钮。点击前不会调用 Replan API；按钮有明确 focus/hover/active/disabled 状态，并与普通自动执行步骤分离。

## 5. 每代 Patch 的内容寻址与独立确认

同一 Task 现在可以先后产生两份不同 Patch。为避免第二代与第一代的可恢复状态相撞，Patch staging 从只按 `task_id` 定位升级为按 `{task_id, manifest_digest}` 内容寻址；内部原子替换的 child identity 同时绑定 Patch manifest，因此两代会生成不同的 replacement/backup 路径。

旧 staging ref 仍可验证并沿用旧 child identity，使升级前已经持久化、尚待确认的 preview 在重启后仍可提交。新 preview 则始终使用内容寻址协议。安全备份不会被删除或覆盖。

新 generation 的 Planner 重新读取第一次写入后的当前文件，形成新的 expected version、proposed content、manifest 和 confirmation digest。提交入口只接受当前 Route 绑定的确认摘要；generation 1 的旧确认即使曾经有效，在 generation 2 激活后也返回 409。

## 6. 正向、反向、篡改与重启语义

新增纵向验收覆盖：

- 第一次 Patch 经用户确认后真实写入，固定测试失败，文件写入事实保留；
- graph 节点保存 `patch_test(test_failed)`，下游取消，condition decision 为 false；
- 浏览器和后台协调器均不自动换代；
- 用户显式请求后 generation 1 Plan 变为 superseded，generation 2 原子激活，旧 Plan/Run/graph 字节级投影不变；
- Replan v3 绑定精确 false decision，Repair Advice 无 grant 且不含失败 `patch_test` source；
- 重放旧确认、重复 Replan、篡改旧 decision digest 均被拒绝；
- 第二代产生不同 staging ref、manifest 和 confirmation，独立确认后测试通过并完成新图；
- 两代 Patch 的安全备份路径互不重叠，当前代重复提交仍幂等。

旧只读目录 Replan、阶段 100 直连补丁、阶段 101 图内批准、阶段 102 条件边与 Workspace staging/recovery 回归均保持通过。

## 7. 数据库与兼容性

本阶段没有数据库结构变化。默认 SQLite 和 Alembic 当前且唯一 head 继续为 `0050_agent_graph_test_conditions`，`alembic check` 无待生成迁移。Replan v1/v2、failure snapshot v1、Repair Advice v1、旧 graph 和旧 Patch staging 摘要均保持兼容；只有新条件失败换代使用 v2/v3 manifest。

## 8. 验证结果

- 条件失败 → 用户换代 → 新 Patch → 新确认 → 固定测试通过的纵向闭环通过；
- 旧确认重放、重复换代、decision 篡改、失败 ResultRef 导入和双代备份碰撞的反向测试通过；
- 后端 pytest 全量收集 81 个测试文件 / 584 项，统一首轮退出 0，12 个既有平台条件 skip；
- Ruff 全仓和严格 mypy 240 个生产源码通过；
- Phase75 保持 11/11、false-success=0、unauthorized-effect=0，v14 baseline compare 无违规；
- 前端 22 个测试文件 / 154 项、type-check 和 production build 通过；
- Alembic 单一 head/current/check、SQLite `integrity_check=ok`、`pip check` 和 diff whitespace 通过。

## 9. 与 Codex/Marvis 的距离

系统现在能在一个持续任务中经历“补丁真实发生 → 测试失败 → 用户决定继续 → 新不可变计划代 → 新补丁再次批准 → 验证成功”，不再要求把失败任务丢弃并手工重建。Plan、Run、graph、ResultRef、condition decision、Workspace manifest 和 approval 都各自保留可审计边界。

当前交互仍主要通过显式 Workbench 按钮触发换代；普通对话中的“继续修复”尚未被绑定为同一 Task 的受控 continuation intent。下一阶段应把这一明确自然语言意图接入同一个 Replan 动作，并保存用户消息证明，同时继续限制为一次换代和每 Patch 独立确认。

# 阶段 116B：持久并行编码循环第六检查点

## 1. 检查点结论

116B 第六检查点没有扩大模型权限，而是补齐第五检查点最关键的韧性证明：同一套服务器预编译的 2～8 文件图已在 Node 八文件上完整走通，并能在每个 Reader/Planner 并行波次后销毁并重建 Coordinator，继续使用原 Plan、Run、Attempt、Handoff 和 verified ResultRef，既不重复已通过步骤，也不把进程内对象当作恢复真值。

本检查点同时修复了八文件真执行暴露的三个运行时缺口：上限图的 Coordinator 输出预算不足、Delivery 对 bounded Coordinator 版本硬编码，以及并行波次出现失败时兄弟 Agent 可能遗留为不可观察的 `running`。这些修复使项目更接近 Codex 类持久多 Agent，而不是转向自由 Shell 或模型自授权。

## 2. Node 八文件上限恢复

- 使用隔离 Node 仓库和八个 `.js` 文件运行完整链：Turn Planner → bounded Coordinator → 4 个 Reader batch → 4 个 Patch Planner batch → exact Patch approval → 固定 Node test → Git approval/commit → Delivery v3。
- 测试在每个双 Agent batch 后新建 `TaskLoopExecutionCoordinator`，最终仍只产生 9 个 Model Turn、8 个 Reader ResultRef、8 个 Patch Proposal ResultRef、一次 Patch/Test/Git 结果和一个 19 节点 Coordinator 图。
- 16 个 Reader/Planner 批节点各只执行一次；重启不会重跑已验证波次，最终 Delivery 精确列出八个文件。
- 对尚未启动的第五个 Reader 篡改持久 binding path 后，下一次 claim 在创建 Attempt 前 fail closed；已通过 ResultRef 保持不可变。

## 3. 上限预算与历史版本兼容

- 真正序列化八文件封存图需要超过旧 `2,000` token ceiling。Compiler 现在按文件数计算 Coordinator 输出预算：双文件继续为 `2,000`，3～8 文件为 `2,200 + 100N`，N=8 时为 `3,000`。
- 新计划使用不可变 `builtin.workspace_bounded_coordinator@1.1.0`，其最大输出为 `3,000`；历史 `@1.0.0` 和旧 Plan/Delivery 仍保留并可精确解析，不改写既有 Contract digest。
- 总 Contract 输出 ceiling 同步包含 Coordinator 与 N 个 Patch Planner 的上限，八文件为 `15,008`，避免 Draft 预算合法但 Contract 总预算不足。
- Delivery 不再猜测当前版本，而是把 ResultRef 的完整 Agent manifest 与当次 `ModelPlannerNodeBinding.effective_authority_manifest.bound_agent` 全等比较。Workbench 投影只负责兼容读取 1.0/1.1，不能替代持久绑定验真。

## 4. 并行失败波次终态收敛

- `execute_agent_batch` 会等待本波次所有协程结束，再按 claim 顺序处理错误并抛出；不会在第一个异常出现后留下仍在后台写库的 sibling tail task。
- 可用但越权的 Patch 提案仍保存稳定失败审计并把对应 Attempt/Invocation/Node/Run 收敛为失败。
- 已派发但 structured outcome 不可判定的兄弟 Agent 会把 Model Turn 和 TaskLoop Attempt 持久化为 `outcome_unknown`，Invocation/Node/Run 同步进入阻断终态，遵守 `NO_AUTOMATIC_REPLAY`。
- 派发前后模型路由被拒绝时也会持久失败，不再遗留 TaskLoop `running`；没有候选结果时 verification 保持 `not_requested`。
- 失败波次之前已经 verified 的 Planner ResultRef 保持不可变；Patch 仍为 `pending`，没有 approval、文件写入、测试或 Delivery。

## 5. 方向校准与诚实边界

这一步提高的是 Codex 类系统的“长期任务可恢复性”，不是表面 Agent 数量：

1. 计划、节点、尝试、模型派发和结果都能跨进程恢复。
2. 并行只发生在服务器封存的独立节点，join 只消费 verified ResultRef。
3. 失败、未知结果和路由拒绝都有持久终态，不靠内存异常传播维持正确性。
4. 历史 Agent 版本与新计划版本并存，恢复时按 exact binding 验真。

仍未开放模型提供 executable/argv/env、自由 Shell、依赖安装、删除、自动 push/PR 或 cloud activation。当前只证明 LOCAL-only/Fake runtime 与隔离仓库语义；它不是 115B 真实 cohort 或 116C 真实模型质量结论。

## 7. 下一执行入口

下一纵切应实现“受控项目探索 → 候选文件集 → 用户确认 → 新的不可变计划代”：

1. Explorer 只使用现有项目根限定的 search/directory/file read，输出 2～8 个候选 exact path 和证据，不获得写权限。
2. 服务器校验同项目、同生态、唯一文件和数量上限，向用户展示候选文件集与理由。
3. 用户确认后生成新的 Contract/Plan generation 和 exact binding；旧 generation、lease 与迟到结果不得进入新计划。
4. 新计划继续复用本检查点已验证的 Coordinator/Reader/Planner/Patch/Test/Git/Delivery 链。

这一纵切完成前，不应通过增加自由 Shell、自动安装或 push 来绕过文件集授权边界。

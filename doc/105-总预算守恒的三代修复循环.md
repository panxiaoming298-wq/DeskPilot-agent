# 阶段 105：总预算守恒的三代修复循环

## 1. 本阶段结论

阶段 105 将阶段 104 的一次性 generation 1→2 扩展为最多三代的对话修复循环。动态 Patch/Test 每次因服务器 `test_passed=false` 阻断后，都必须重新取得一条精确 active user message，创建新的 Plan、Run、graph、Workspace staging manifest 和 Patch confirmation。系统不会自动换代，也不会让旧 confirmation、Patch receipt、失败测试或 Repair Advice 取得新一代写权限。

```text
GEN 1 false decision + user continuation + fresh confirmation
                              ↓
GEN 2 false decision + user continuation + fresh confirmation
                              ↓
GEN 3 pass → delivery
     或 false decision → hard stop（不再保存 continuation）
```

## 2. 合同硬上限

新建 `workspace_dynamic_patch_test` Task Contract 使用两条冻结约束：

- `maximum_three_patch_plan_generations_v1`：同一 Task 最多 generation 1、2、3；
- `cross_generation_task_budget_v1`：所有代的 Plan 节点和动态子图节点共享同一个 TaskBudget。

旧阶段 104 合同的 `one_user_requested_condition_failure_replan_v1` 仍按 generation 2 封顶，旧 Replan v1～v4 的摘要和读取规则保持兼容。只读目录失败的原一次性 Replan 也不扩大。

第三代再次失败时，Workbench 不再公开 enabled `replan_failed_execution`。按钮端点和确定性“继续修复”对话都会在写入新 Conversation Message 前返回 409；用户若仍要继续，必须提交一条完整的新任务指令，建立新的 Task 和预算边界。

## 3. 跨代总预算

阶段 104 的校验只证明单个 Plan 或单个 Run 没有超过 TaskBudget；重复编译相同 Plan 会隐式重复获得额度。阶段 105 将动态 Patch Task 的固定三代预算在 Task 创建时一次性声明，并在两个位置累计核算：

1. Replan 激活前，Planning Service 汇总 source generation 及之前所有持久化 execution node allocation，再加入目标 Plan 的基础节点预算；总和超过 TaskBudget 时拒绝创建新代。
2. Supervisor 接受新动态 DAG 前，汇总同一 Task 从 generation 1 到当前 generation 的全部 Plan/动态图节点预算，再加入候选图预算；任何维度超过合同都拒绝封图。

累计维度包括 model calls、tool calls、input/output tokens、wall seconds、retries、cost micros 和 handoffs。`max_plan_nodes` 继续表示单代结构上限，不被误当成可跨代相加的费用额度。

## 4. Replan v5 预算证明

新循环使用 `deskpilot.agent-replan.v5`，在 v4 的 failure snapshot、无授权 Repair Advice 和 continuation intent 之外增加 `AgentReplanBudgetProof v1`：

- 合同摘要和最大 Plan generation；
- source/target generation；
- TaskBudget 总上限；
- 换代前已经分配的累计预算；
- 目标 Plan 基础分配；
- 激活后累计值和剩余额度；
- 内容寻址 budget digest。

每次读取 Replan 都从不可变 Plan、Run 和 execution node 记录重新计算该证明。即使攻击者同时重算 budget proof 和 Replan 顶层摘要，只要累计值与持久化分配不一致，读取仍以 `PLANNING_PROOF_REJECTED` fail closed。

## 5. 每代独立授权

generation 2 只能引用 generation 1 的精确 false decision 和当次用户消息；generation 3 只能引用 generation 2 的精确 false decision 和另一条用户消息。Repair Advice 的 grants 始终为空，失败 `patch_test` ResultRef 继续从可导入 source 中排除。

新一代重新读取已经被前代补丁修改过的当前文件。Workspace staging ref 按 Task 和 manifest digest 内容寻址，因此三代的 staging ref、manifest digest 与 confirmation digest 均不同。任何旧 confirmation 在当前等待节点上重放都会被拒绝。

## 6. Workbench 信任投影

Workbench 新增服务器生成且进入 projection digest 的 `AgentRepairLoopStatus v1`，公开：

- 当前 Plan generation / 最大 generation；
- 剩余换代次数；
- 已分配 / 总 model、tool、cost 等预算；
- 下一 Plan 的固定基础分配是否仍可由剩余预算覆盖；
- `AVAILABLE`、`GENERATION_LIMIT_REACHED` 或 `CROSS_GENERATION_BUDGET_EXHAUSTED` 原因码。

前端批准卡显示下一代编号、剩余次数、false decision 和预算计量条；达到上限后改为不可操作的明确阻断卡，不把安全终止伪装成普通失败或无限重试。

## 7. 兼容性与数据库

- Replan v1～v4 继续按原字段集合计算摘要；v4 不要求 budget proof。
- Replan v5 必须同时包含 continuation intent 和 cross-generation budget proof。
- graph v1～v7、failure snapshot v1/v2、Repair Advice v1/v2 均未改变。
- 本阶段只增加 JSON manifest 和 Workbench projection 字段，没有新增表或列；Alembic head 继续为 `0050_agent_graph_test_conditions`。

## 8. 固定验收

新增固定端到端用例覆盖两种三代结局：前两代失败、第三代通过并交付；三代全部失败后达到硬上限。测试逐代断言 exact false decision、独立 continuation message、Replan v5 budget proof、不同 staging/manifest/confirmation、旧确认拒绝、失败 ResultRef 不导入、原 Task/旧 Plan/Run/graph 不改写，以及上限后按钮/对话均不产生第四代或多余用户消息。

最终门禁结果：

- 后端 81 个测试文件 / 593 项，修复兼容门控后的统一全量为 `581 passed + 12 skipped`、退出 0；
- Ruff 全仓和严格 mypy 240 个生产源码通过；
- Phase75 11/11、false-success=0、unauthorized-effect=0，v14 baseline compare 通过，report digest 为 `2154929e74b0d63710bb57e94d6a0d5c74d426ae5483a02d899f705da87bb8b6`；
- 前端 22 个测试文件 / 154 项、type-check 和 production build 通过；
- Alembic 当前且唯一 head 为 `0050_agent_graph_test_conditions`，autogenerate 无待生成操作；
- SQLite `integrity_check=ok`，`pip check` 与 diff whitespace 通过。

## 9. 下一步

下一阶段优先把当前严格的单 Patch 节点修复推广到通用动态任务图中的可组合 Patch/Approval 节点，同时保持每个写节点独立确认、总预算/代数上限和服务器 verified edge；随后再接入 live model/Judge-human cohort 校准动态图提案和修复质量。
